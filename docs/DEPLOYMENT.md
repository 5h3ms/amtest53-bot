# Публикация в Firebase

Публиковать после локальной проверки с реальным тестовым Telegram-ботом. Код привязан к отдельному проекту `amtest53-bot`. Команды ниже создают/обновляют облачные ресурсы; это отдельный этап после настройки биллинга и секретов владельцем.

## 1. Проект и доступ

1. Войдите в нужный Google-аккаунт: `npx firebase login`.
2. Проверьте `npx firebase projects:list`. Цель — только `amtest53-bot`.
3. В консоли этого проекта подключите Blaze. Настройте месячные уведомления о расходах на $5, $8 и $10. Это уведомления, а не общий жёсткий лимит.
4. Создайте Firestore Standard в Native mode, регион `europe-west1`, правила production/deny-all. Доступ нужен серверной identity бота, а не клиентам напрямую.

## 2. Секреты

```powershell
npx firebase functions:secrets:set BOT_TOKEN --project amtest53-bot
npx firebase functions:secrets:set WEBHOOK_SECRET --project amtest53-bot
npx firebase functions:secrets:set ALLOWED_USER_IDS --project amtest53-bot
npx firebase functions:secrets:set ADMIN_USER_IDS --project amtest53-bot
npx firebase functions:secrets:set ACCESS_MODE --project amtest53-bot
```

Значения вводятся в приглашения CLI, не в текст команд. `WEBHOOK_SECRET` — случайная строка из не менее 32 символов A–Z/a–z/0–9/_/-. Сохраните её также локально в `.env.local` для регистрации webhook; не используйте токен бота как этот секрет. `ACCESS_MODE=public` открывает личный чат с ботом каждому пользователю; `private` ограничивает доступ списком `ALLOWED_USER_IDS`. `ADMIN_USER_IDS` всегда содержит только явные ID администраторов; в закрытом режиме они также должны входить в список участников. При изменении секретов обе функции нужно опубликовать заново.

Не создавайте и не коммитьте JSON-ключи service account. Cloud Functions используют штатную identity. Для IAM предоставляются только нужные права: чтение заданных секретов и доступ к Firestore. Прямой доступ клиентов запрещён в `firestore.rules`.

## 3. Проверки и публикация

```powershell
npm ci
npm run check
npm run build
npm run test:emulator
npx firebase deploy --only functions:amtest53,firestore:rules,firestore:indexes --project amtest53-bot
```

Появятся HTTPS-функция `telegramWebhook` и расписание `maintenanceSchedule`. Для webhook необходим публичный HTTPS-вызов (Telegram не использует Google IAM); проверка секретного заголовка выполняется внутри функции до обработки. Расписание вызывается Cloud Scheduler с его штатной аутентификацией.

При первой публикации CLI может подтвердить создание функций и затем завершиться с сообщением об отсутствующей политике очистки образов. Настройте её отдельно; уже созданные функции повторно публиковать для этого не нужно:

```powershell
npx firebase functions:artifacts:setpolicy --location europe-west1 --days 7 --force --project amtest53-bot --non-interactive
```

После публикации запишите фактический URL `telegramWebhook` в `.env.local` как `WEBHOOK_URL`. Не угадывайте URL по имени проекта. Убедитесь, что локальный `npm run dev` остановлен, затем:

```powershell
npm run telegram:webhook
```

Команда регистрирует адрес, включает проверку отдельного секрета и последовательную доставку (`max_connections=1`), затем проверяет результат. Она отказывается заменять другой уже установленный webhook.

## 4. Проверка в Telegram

- `/start`, новый урок, перевод, ответ, переход к следующей карточке.
- Новый пользователь без записи в списке доступа для `public`; два разрешённых и один неразрешённый участник для `private`. Административные команды доступны только явным администраторам в обоих режимах.
- Повторное нажатие старой кнопки и повтор webhook не меняют счёт дважды.
- Пробный тест и сохранение результата; тестирование таймера автоматизировано.
- `/remind HH:MM Asia/Yerevan`, доставка и отключение напоминаний.
- Перезапуск/новая публикация функции сохраняет прогресс.
- `/path`: следующий урок использует экзаменационный маршрут, разбор вопроса учитывается как помощь, пробный тест её не открывает.
- Повторение вопросов после ошибки, ранний правильный ответ без повышения освоения, прогресс по темам.
- `/stats` и `/reports`: работают только для администратора; сообщение об ошибке сохраняет конкретное задание, а старые кнопки формы безопасно отклоняются.
- Новые счётчики начинаются с обновления и не восстанавливают старую историю. Автоматическое завершение теста не считается пользовательской активностью.

Локальный polling не работает одновременно с webhook того же бота. Для дальнейшей разработки используйте отдельного тестового бота с другим токеном; рабочий webhook автоматически не удаляется.

## 5. Обслуживание

Настройте ежедневную резервную копию Firestore с хранением семь дней; проверьте восстановление в отдельную тестовую базу, не перезаписывая рабочую. Доступ к резервным копиям такой же ограниченный, как к пользовательским данным. Локальную копию `.local/state.json` делайте при остановленном процессе и храните вне Git.

Проверьте журналы двух функций, отчёт Cloud Billing, число вызовов и операций Firestore. Функции не держат постоянно прогретый экземпляр. Ограничения экземпляров и бюджетные уведомления снижают риск расходов, но не являются полным денежным потолком проекта. Не включайте подробное логирование Telegram-запросов, заголовков или переменных окружения.

Для обновления: ветка → проверки/PR → merge → ручная публикация точных функций и правил. Для отката верните предыдущий проверенный коммит и опубликуйте его; снимок учебных вопросов в активной сессии сохраняется. Перед изменением схемы хранилища сначала подготовьте миграцию и резервную копию.

## Переход на выборку наступивших событий

Операционные подробности и стоимость запросов описаны в [FIREBASE-USAGE.md](FIREBASE-USAGE.md). При первом выпуске этой оптимизации:

1. Сохраните приватную резервную копию пользовательских документов вне Git. Опубликуйте `firestore:indexes` и обе функции из одного проверенного коммита. После успешного обновления обеих функций подождите ещё 120 секунд: уже начатый запрос прежней версии может завершиться позже и перезаписать документ без метаданных.
2. Запустите предварительную проверку с существующей ADC-авторизацией оператора. Ключ service account не требуется; токены и содержимое локальных credentials не выводите:

   ```powershell
   npx tsx scripts/backfill-maintenance.ts --project amtest53-bot
   ```

3. После проверки количества записей выполните перенос служебных метаданных:

   ```powershell
   npx tsx scripts/backfill-maintenance.ts --project amtest53-bot --apply
   ```

   Скрипт перечитывает каждый документ в транзакции, обновляет только `nextMaintenanceAt` и `maintenanceIndexVersion`, проверяет все записи и работоспособность индексированного запроса. `stateJson` с прогрессом не переписывается. Только после успешной проверки публикуется `meta_maintenance_index_v1` с `ready:true`. Итог должен содержать `readyPublished:true` и нули ошибок. Повторный запуск безопасен. До готовности метаданных расписание продолжает прежний обход, чтобы не потерять таймеры и напоминания.
4. Проверьте успешный запуск расписания, обе ACTIVE-функции, webhook и нулевую очередь ошибок Telegram. Не перерегистрируйте уже работающий webhook при обычном обновлении.

Перед откатом на версию, которая ещё не записывает метаданные, отключите использование индекса:

```powershell
npx tsx scripts/backfill-maintenance.ts --project amtest53-bot --disable-index
```

Затем публикуйте предыдущую версию. При повторном переходе на оптимизированный код снова выполните проверку и `--apply` после обновления обеих функций. Чтение маркера выполняется на каждом запуске расписания, поэтому его отключение действует и на уже прогретые экземпляры. Скрипт допускает только этот production-проект либо `demo-*` с локальным эмулятором; значения пользовательских записей и секреты не выводятся.
